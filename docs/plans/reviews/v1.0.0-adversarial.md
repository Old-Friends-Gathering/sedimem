# v1.0.0-refactor.md（v2）对抗审核

审核人：agent-33（对抗位）· 2026-11-14 · 对象：docs/plans/v1.0.0-refactor.md（下称"计划"）

## 0. 阻断项（不修不能开工）

- **B1｜异步派生没有队列与执行模型，CLI 单次进程下等于永远不派生**。计划 §2.3 D1「`write` 落盘后异步（不阻塞返回）」；但 CLI 是写完即退的短命进程（`versions/v0.6/src/cli/memo.js:569,589` 直接 `process.exit`）。fire-and-forget 的 Promise 在进程退出时被砍。计划全文没有：派生任务持久化队列、谁来 drain（MCP 常驻？nightly？下次 CLI 启动补跑？）。三种执行模型（memo CLI 单次进程 / MCP 常驻 / nightly）只有 MCP 常驻能吃掉异步任务，而 memo write 是主写入路径。必须补：落盘即入队（复用裁决 70 的 capture queue 模式）+ `memo derive --drain` + nightly 补跑，三者至少其二。
- **B2｜D1 输出 schema 要求 `kind`，与「applyDerivation 物理上不接受 truth 字段」自相矛盾**。计划 §2.2（L86-87）「derive 模块导出表里没有 truth 写入函数」；§2 研究文档 schema（llm-summarization-pipeline-2026.md:51-55）`required: ["title","summary","kind","spo"]`。`kind` 是真相层字段（裁决 49：唯一真相在 policy.kinds）。要么 LLM 的 kind 只是「建议」需与写入 kind 一致性校验，要么 applyDerivation 得能写 kind——二者必居其一，现在两处文本打架。
- **B3｜`derived` 的存储位置未定义，I44「真相层 hash 逐字节不变」可能物理不可能**。若 derived upsert 进 `items/<scope>.jsonl` 的记录行（最自然实现），真相层文件字节必然变化；若是旁路文件，则裁决 39「常驻读端必须显式刷新视图」+ 裁决 55「视图可字节重建」的整套机制要重新对 derived 生效。计划只字未提 derived 存哪。这是 W3 的第一张表都画不出来的程度。
- **B4｜D2 默认用 LLM 裁决，违反裁决 50「JudgePort 默认实现必须确定性、无 LLM」**。docs/02-data-model-and-contract.md:584-591：`ruleJudge` 是默认，自定义裁决器**只能经 `createMemoryService({judge})` 注入，不得读环境变量**。计划 §2.3 D2 把 LLM 当默认路径、ruleJudge 当失败回落，方向颠倒；「灰区路由大模型」若靠 `MEMO_LLM_*` 环境变量切换裁决行为，直接踩「不得读环境变量」红线。改法：LLM judge 必须显式注入且默认关。

## 1. 「LLM 接管总结」的收益证据

- **I43「Recall@5 +8pp」无任何实测或文献支撑**。检索全部三份研究文档，唯一出处是 llm-summarization-pipeline-2026.md:96——那是**待办设计**（"构造金标集 40 条……阈值 ≥8pp"），不是测量值。CLM 论文（clm-paper-2026.md）的 +11.4% 是 BrowseComp-Plus 任务分，与 BM25 检索召回无关。8pp 是拍脑袋数。
- 更深的问题：**金标集和阈值都是自己造的**，40 条查询里 3 条翻转就是 ±7.5pp，阈值恰好卡在噪声量级——通过了证明不了收益，不通过了也未必真差。这是自欺式验收。建议改为：先在 v0.6 真实库上跑无派生基线并留档，基线 Recall@5 已 ≥90% 时改报「Recall@1 提升」或「首条命中位次提升」，并把金标集交给非作者 agent 盲测。
- I41「保留率 ≥90%、变形 ≤5%」用第二个 LLM 判分，LLM-as-judge 的偏差未讨论（判断）。

## 2. 异步派生 × 三种执行模型

- 见 B1。补充：MCP 常驻进程派生成功后，CLI/Web 读端看到 derived 需走裁决 39 的 refreshView；计划未提。D4 brief「nightly 生成」是计划中唯一承认 nightly 执行模型的地方，但 nightly 现在无 LLM（`src/cli/nightly.js:3`「确定性夜间整合（无 LLM、无随机）」注释与 D4 矛盾，注释需同步改，否则文档漂移——恰是本计划要治的病）。

## 3. 大版本绑定与回滚

- **波次并非独立**：W1 写盘 `src/api/*`，W3 又写 `src/api/write-path.js`+`maintenance.js`（计划 L130/L132）；W2 改的 scope 调用点与 W3 的派生落盘同文件。跨波文件重叠意味着 W3 出问题 revert 会连带 W1 的接口改动——「每波独立 PR + eval 对比」只能发现行为回归，不能保证 revert 干净。
- 回滚路径只写了「`main` 可回滚」（L172），对**数据**回滚只字未提：v1.0 运行期间产生的 derived 字段/派生事件混入真相层与事件流后，回滚到 v0.6 代码时这些字节是否被旧 reader 容忍？裁决 46「curate status 只从事件流聚合」——v1.0 新事件类型（derive 系）在 v0.6 的统计里是未知类型，聚合口径未定义。应补一条：v1.0 落盘的新字段/新事件必须让 v0.6 reader 只警告不崩（向后兼容测试进 G6）。
- 「换图谱 + LLM + 拆依赖 + 文档重写 + 换版本目录」五事同船，任何一波翻车都阻塞发版。见 §6 砍法。

## 4. 与既有裁决冲突（除 B4 外）

- **裁决 71/73（title 纪律）**：v0.6 方向是「调用方必须给 title、v0.7 默认硬拒」（record.js:113-117 注释明说）。D1 自动派生 title 会让调用方永远不写 title——把一条已冻结的行为契约（`E_TITLE_MISSING` 警告→强制）实质废掉，且无 ADR。至少要写：derived.title 只在 title 缺失时兜底，不豁免 titleEnforce。
- **裁决 75（完全手动）与 D3 `--auto`**：计划 L105 称「用户 v0.6 裁决不变：只有 --auto 显式开启」，但 §2.3 表内 D3 触发条件「--auto（新增 ≥16k token）」读起来是开了 --auto 之后按 token 自动反复触发——「每次运行显式」还是「一次开启持续自动」两种语义天差地别，后者改写了裁决 75，需 Lead 明确裁决。
- **裁决 54（sourceRefs）**：LLM 建议的 SPO 若落 derived.spo 不受影响；但若未来喂给 L3/画像，须走 sourceRefs 强校验——计划未提，暂记建议。
- 裁决 46 与 D2 兼容（候选仍来自 dedupeScan），无冲突。

## 5. 遗漏的失败模式

1. **派生层陈旧（stale derived）**：原文被 supersede/merge 后，败者的 derived.title/summary 仍被检索与 brief 使用——检索命中一条「已被取代的记忆」的旧标题，比没有标题更糟。计划无失效钩子（curateApply/supersede 应连带标记 loser 的 `deriveStatus:'stale'` 或从索引摘除）。
2. **checkpoint 幻觉 nextSteps**：I45 的正则（动词开头 + 无「也许/可能」）挡不住「运行 npm test 验证 X」这种看似可执行实则虚构的条目；研究文档 §5 的「后续引用率 ≥50%」是离线脚本却不进 W4 完成判据（计划 L133 只到 I45）。建议把引用率检查挂进 tools 并纳入验收。
3. **transcript 跨会话串味**：DSH 按 cwd-slug 分目录（session-llm-checkpoint-2026.md:10），同一 cwd 下多 session 并存（含 subagent 会话）；读取器若只按目录不按 session id 过滤，会把别的会话轮次读进来。W4 判据（L133）没有「只含本 session 行」的断言。Claude 行结构本身未验证（同文 :12）。
4. **LLM 输出违反 kind 语义**：把 gotcha 写成 fact 之类，与 B2 相关；此外 derived.tags 无词表约束，可能生成「紧急!!」这类污染 brief 排序的标签（判断/未验证）。

## 6. 如果只能保留三波

**保 W1（解耦）、W3（LLM 层）、W6（收口发版）**。

- W1 是所有后续波的地基（arch-boundaries + 单向依赖），不先做 W3/W5 都是在坏地基上加层。
- W3 是用户本版的核心诉求（m00001 立项原文「加入 LLM」），砍掉则 1.0.0 无意义。
- W6 是发版机械动作，不可省。
- **砍 W0（文档治理）**：Q14 门禁有价值但不阻塞代码；可拆成独立小版本（v1.0.1），且「文档漂移」恰因把 8 份调研+计划全堆进 docs 才加重——先治代码再治文档。
- **砍 W2（core 去重）**：纯内部整洁，无行为收益（计划自判据就是「eval 分数不变」），是典型的可无限期推迟项。
- **砍 W4（会话库 LLM）**：幻觉风险最高（§5.2/5.3 两个失败模式都落在这）、收益最间接、且与裁决 75 有语义拉扯；D3/D4 依赖的 transcript 格式有一家未验证。等 W3 的 derive 基础设施在主库跑稳一版再上。
- **砍 W5（拆大文件+换图谱）**：`mcp/server.js` 860 行确超 400 线（实测 `wc -l`），但拆分是 косметic 改动；force-graph 替换有独立回归风险（计划自己也列了风险表 L173），最不该和 LLM 同船。

## 7. 结论

计划的研究底子和「真相层不可变」主线是扎实的，但 W3 的可施工性存在 4 个阻断级空洞（B1–B4），验收阈值 I43 无证据，波次绑定过重。建议：先修 B1–B4 并补数据回滚兼容条款，再按 §6 裁剪波次后放行。
