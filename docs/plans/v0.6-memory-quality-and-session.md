## 0. 三条需求的共同点

用户的三条抱怨，本质是同一个问题的三个切面：**记忆库「写给谁看」没有区分**。

| 需求 | 现状病灶 | 本质 |
|---|---|---|
| ① 记忆点要明确简要 | 一条记录可以塞 4000 字长文（`MAX_TEXT`），`title` 可省略，brief 里退化成「前 60 字」 | 记录粒度 = 「一个可判断的事实」，不是「一段话」 |
| ② 要临时记忆库 | 只有长期库；30k token 后的压缩发生在**上下文里**（DSH 的 auto-compact），落不到盘上 | 需要一个**会话级、可丢弃、可晋升**的中间层 |
| ③ 切页丢分库 | `ui/app.js:520` 切 tab 时 `location.hash = '#/'+r` 丢掉 `?scope=` | 分库应当是**全局状态**，不是页面参数 |

三条互相咬合：②的会话库必须写「短记录」才有意义（①），②的库要在 UI 里能看见（③）。

## 1. 方向 A：写入侧契约（记忆点更明确）

### 1.1 问题量化（调研结论）

- `versions/v0.5/src/core/record.js` 的 `MAX_TEXT = 4000`，**超长静默截断**（v0.1 就有的行为）；
- `title` 字段可选 → MCP 的 `INSTRUCTIONS` 再三要求但无法强制；
- brief 渲染对非结构化记录退化成 `text.slice(0, 60)`；
- 外部参照：Mem0 prompt 要求 15–80 词/条（`PAST_MESSAGE_TRUNCATION_LIMIT=300`）、basic-memory 一行一 observation、dsh-auto-memory Tier-1 140 字符 / Tier-0 ≤800 token（实测语料 p90 = 1196）。

**结论：读侧三级披露已经不错，短板在写侧没有「粒度纪律」。**

### 1.2 设计（方案 A：只改写入契约，不改存储）

策略全部进 `config/policy.json` 的 `write` 段（**不写死**）：

```json
"write": {
  "titleMaxChars": 40,
  "valueRecommendChars": 300,      // 软线：超了就提示 + 打 tag，不拒绝
  "textHardMaxChars": 4000,        // 硬线：超了报错（不再静默截断）
  "oneFactOneRecord": true,        // 开启后写入门控做「一句话判断」
  "longFormTag": "long-form"
}
```

新增三条行为：

1. **`title` 变成结构化记录的必需字段**（`kind=fact|decision|gotcha|pref`）；缺失 → `E_INVALID_RECORD`，错误信息直接给可复制的最小正确形状。`kind=state` 与自由文本（`text`）豁免。
2. **软线提示而非拒绝**：`value`/`text` 超过 `valueRecommendChars` → 写入成功但返回 `warnings: [{code:'E_RECORD_LONG', message:'建议 ≤300 字，长文请拆成多条或改用 state', splitSuggestion: <前 3 句>}]`，并打 `long-form` tag（可被 `memo search --tag -long-form` 审计）。
3. **硬线不再静默**：超过 `textHardMaxChars` → 抛 `E_RECORD_TOO_LONG`（带 `truncateTo` 建议）。这是行为变更，写进 CHANGELOG 的 Changed。

同时改 brief 渲染（`src/render/brief.js`）：结构化记录优先 `title`；无 title 时用 `subject · predicate` 而非 `text.slice`。

### 1.3 验收

- I37 `i37-brevity-contract`：缺 title → 拒；301 字 value → 成功 + `E_RECORD_LONG` warning + `long-form` tag；5000 字 text → `E_RECORD_TOO_LONG`；brief 里长文记录只出现 title 行。
- 单测：`policy.write` 缺省与覆盖、`state` 豁免、`splitSuggestion` 切句正确（中英文标点）。

## 2. 方向 B：开发临时记忆库（session scope）

### 2.1 关键事实（调研核实）

- DSH 侧已有 `@deepseek-ai/dsh-compaction-basic`（`thresholdRatio 0.8` / `retainRatio 0.16` / per-model `retainTokens`）与 `compaction/summary` 事件，payload 含 `{compactionId, summary: ContentBlock[], shadowedRange, shadowedSeqs, shadowedTokenCount, provider, model, usage?}`；
- **我们不复制它的压缩算法**，只做两件事：①把「已经压出来的摘要」接住落盘；②给还没压缩的会话提供 8 段 checkpoint 模板（agent 自己填）。

### 2.2 数据模型

新 scope 前缀 **`session:<id>`**（`id` = `YYYYMMDD-HHmm-<4hex>`，创建时生成）。

| 概念 | 记录形态 | 说明 |
|---|---|---|
| session 元信息 | `kind=state`, `subject=session`, `predicate=meta`, `value={"id","title","startedAt","cwd","repo","status":"open\|closed"}` | 唯一一条，可 supersede |
| checkpoint | `kind=state`, `subject=session`, `predicate=checkpoint`, `value` = 8 段 JSON | 每次压缩/手动都追加一条新版本 |
| 期间事实 | 常规 `kind`（fact/decision/gotcha） | 但**默认 `ttlMs` 由 policy 决定**（建议 7 天） |
| 交接候选 | `kind=decision`/`gotcha` + `tags:['promote-candidate']` | close 时晋升到主库 |

8 段 checkpoint（冻结）：

```json
{ "intent": "", "concepts": [], "files": [], "errorsAndFixes": [],
  "pendingJobs": [], "currentState": "", "nextSteps": [], "criticalContext": [] }
```

### 2.3 CLI 与工具（跨三端，都走 MCP + CLI 双入口）

| 命令 / 工具 | 作用 |
|---|---|
| `memo session start --title <t> [--repo <path>]` / `memory_session_start` | 建 session scope，写 meta，返回 scope 名与「请把它设为当前写库」提示 |
| `memo session checkpoint [--file <json>] [--from-summary <file>]` / `memory_session_checkpoint` | 追加 8 段 checkpoint 新版本；`--from-summary` 直接从 DSH 的 `compaction/summary` JSON 抽字段 |
| `memo session status` / `memory_session_status` | 打印 checkpoint 段数、期间事实条数、距上次 checkpoint 的写入数 |
| `memo session close [--handoff <path>]` / `memory_session_close` | 生成交接文档 + 晋升白名单 kind 到主库 + 其余记录 tombstone（保留 30 天可 restore） |
| `memo session sweep --older-than 14d` | 兜底：自动关闭僵尸 session（**只报警不删**） |

**不做**：不做自动触发（不 hook pre-step 自动建库、不在 30k 自动压缩）——会话库的价值是「我知道自己在做什么」，自动化的边界只到「提示」。

### 2.4 插件侧（可选，默认关）

`plugin/dsh-sedimem` 增加 `sessionObserver`：
- 监听 `compaction/summary`，把摘要直接写成一条 checkpoint（**无需额外 token，DSH 已经付过**）；
- 检测到会话 token 使用 > `session.hintTokens`（默认 30000）时，在 `systemPrompt.context` 里加一行「建议执行 `memory_session_checkpoint`」；
- 开关 `session.autoWatch`（默认 false）。

### 2.5 关闭与交接

`memo session close` 产出 `docs/handoffs/<session-id>.md`（模板六节：做了什么 / 关键决策 / 踩过的坑 / 改了哪些文件 / 未完成事项 / 下次开工入口），并：

1. 白名单 kind（`decision` / `gotcha`）写入**主库**，`tags:['from-session:<id>']`；
2. checkpoint 的 `nextSteps` 写成主库一条 `kind=state, subject=session, predicate=handoff`；
3. 其余记录 tombstone（`forget --reason session-closed`），保留 30 天可 `restore`。

### 2.6 验收

- I38 `i38-session-lifecycle`：start → 写 5 条 → checkpoint → close → 主库多出 2 条（decision/gotcha）+ 1 条 handoff state，session 库只剩 meta + checkpoint 墓碑；handoff md 存在且六节齐全；重复 close 幂等。
- I39 `i39-session-scope-isolation`：session 库的记录**不出现在**主库的 brief / search（除非显式 `--scope`），反之亦然。

## 3. 方向 C：UI 分库粘性

### 3.1 根因

`versions/v0.5/ui/app.js:520` 切 tab 时 `location.hash = '#/' + route`，**丢掉 `?scope=`**；读侧只有 `currentScope()`（`:18`）从 hash 取。所以每切一次页面就回到默认分库。

### 3.2 设计

1. 新增 `versions/v0.6/ui/scope.js`（纯函数，可单测）：
   `resolveScope({ hashScope, storedScope, serverDefault, available })` → 三级回落：URL 显式 > localStorage > 服务端默认；非法/不存在则回落并返回 `fallbackReason`。
2. `app.js` 改成「分库是全局状态」：`setScope(scope)` 写入 localStorage（`sedimem.scope`）+ 重写 hash（保留 route）+ 刷新各页；所有内部导航**必须**带 scope（加一个 `hrefFor(route)` 统一出口，禁止再手拼 `#/route`）。
3. 服务端 `/api/scopes` 返回 `{scopes, default}`，前端首次加载时用它校验 localStorage 里的分库是否还存在（库被删 → 回落并提示一次）。
4. UI 顶栏下拉沿用，但切换后**不再跳页面**，只重载当前页。

### 3.3 验收

- I40 `i40-scope-stickiness`：CDP 起真服务 → 选 `dir:b` → 依次点四个 tab → 每页请求都带 `scope=dir:b`；刷新页面仍是 `dir:b`；localStorage 里存的非法 scope → 回落 `serverDefault` 且控制台只提示一次。
- 单测：`resolveScope` 的 6 种组合（含非法、空、多分库同名）。

## 4. 数学 / 金融方法：只取三条能落地的

调研（`math-methods-2026.md` / `finance-methods-2026.md`）筛完只剩三条值得做，且都**不引入新依赖**：

| 结论 | 落在哪 | 代价 |
|---|---|---|
| **生存分析校准 `halfLifeMs`**（按 kind 的「被 supersede 的时间分布」估中位寿命，而不是拍脑袋 30 天） | `nightly` 里加 `calibrateDecay()`，只写日志与 `metrics`，**不自动改 policy**（人决定） | ~40 行 |
| **滞回双阈值压缩**（上阈值触发、下阈值才允许再触发，防抖） | sessions 的 checkpoint 提示逻辑 | ~20 行 |
| **补 token 埋点**（`brief`/`checkpoint` 的实际字符数进 metrics，为 R(D) 曲线留数据） | `nightly` metrics 加两列 | ~15 行 |

明确**不做**：Kelly 公式（我们不是连续下注场景）、MDP/IB 求解器（数据量不够）、在线 Markowitz（无组合概念）、VaR（记忆库没有「风险敞口」语义）。

## 7. 风险与回滚

| 风险 | 处理 |
|---|---|
| 强制 title 破坏现有三端写入 | 只对 `kind≠state` 的结构化记录强制；MCP `INSTRUCTIONS` 先改成「必须给 title」；v0.6 起 30 天内 `legacyTitle` 兼容开关（policy 可关） |
| 300 字软线只是「提示」，用户可能忽略 | brief 渲染侧做真实收益：长文记录只出 title；`memo stats` 增加「long-form 占比」指标，长期看趋势 |
| session 库被误当主库（写进去就丢） | 创建时 `memory_session_start` 明确返回「这是临时库，close 时只晋升 decision/gotcha」；brief 在 session scope 下顶部加一行警示 |
| UI 粘性导致「看不到自己想看的库」 | 顶栏永远显示当前分库全名；提供「跟随当前 git 仓库」快捷项 |
| 一次改三件事审不过来 | 五波次分批 PR（每波 ≤1 个独立 PR，双审核），W5 统一发版 |

## 8. 明确不做

1. **不自动建库、不自动压缩、不自动关闭**（用户明确要求手动触发）；
2. 不做跨机同步；
3. 不引入 embedding / LLM（成本调研已备，留到 v0.7 按需开启）；
4. 不改动 append-only 真相层语义（session 也是一样，只有 tombstone）；
5. 不做「自动总结会话」——checkpoint 由 agent 或人写，我们只提供模板与落盘。

## 9. 我建议的批准粒度

如果只想先尝一口：**只批 W1 + W4**（写侧契约 + UI 粘性），大约 1 天，风险最低，立刻能感受到「记忆点变短」和「切页不丢库」；
W2/W3（临时记忆库）是真正的结构性改动，建议单独一轮确认后再做。
