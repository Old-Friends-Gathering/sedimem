## 0. 三件事的共同点

三件事都在问同一个问题：**在有限的注意力/上下文预算下，怎么让记忆更值钱**。
所以本版不止加三个功能，还要把「值不值」变成可测的数字——否则下一版又会凭感觉调。

## 1. 方向 A：让每条记忆短而明确（写侧契约）

**结论先行**：读侧已经省（`tier0` 800 字符一条一行、`brief` ≤80 行、`memory_get` 按需取全文），
短板在**写侧**——现在允许一条 4000 字符的长段塞进多个事实，而且超长是**静默截断**。

### A1 契约（改 `versions/v0.6/src/core/record.js` + `config/policy.json`）

| 规则 | 值 | 行为 |
|---|---|---|
| `value` 上限 | **300 字符** | 超限 → `E_VALUE_TOO_LONG`，错误信息给「拆成几条」的示例；不再静默截断 |
| `text` 软限 | **600 字符** | 超限不拒，打 `long-form` 标签（可查询、可统计） |
| `text` 硬顶 | 4000（保留） | 超硬顶仍拒（防滥用），但错误码从静默截断改为 `E_TEXT_TOO_LONG` |
| `title` | 结构化记录**必填**（≤40） | 缺 → `E_TITLE_REQUIRED`；这是 `makeLabel`、`brief`、图谱标签的唯一可信来源 |
| 疑似多事实 | unstructured 且按 `。；;.` 切分 >3 句 | 写入成功，返回**可直接重放的** `splitSuggestion: string[]`（每句一条建议记录）+ `factsSuspected: N`（软信号，不阻断） |

### A2 MCP 工具描述与 `INSTRUCTIONS`

`memory_write` 的 schema 描述改写为：「**一条记忆只记一个事实**；多事实请多次调用；
`value` ≤300 字；结构化记录必须给 `title`」。`INSTRUCTIONS` 补一条「写入前先问：这句话能不能再拆？」

### A3 验收（机械）

`eval` 新增 **I37 `i37-brevity-contract`**：
1. 301 字 `value` → 拒，错误码 `E_VALUE_TOO_LONG`；
2. 700 字未结构化 `text` → 写入成功且 `tags` 含 `long-form`；
3. 结构化记录无 `title` → `E_TITLE_REQUIRED`；
4. 4 句长文 → `factsSuspected >= 3`；
5. 存量长记录（v0.5 迁移来的）**仍可读、可 search**（向后兼容）。

指标（`stats` + nightly 快照新增）：`meanTextChars`、`p90TextChars`、`longFormRatio`、`titleCoverage`。

### A4 存量数据

**不改写真相层**。迁移只做两件事：给现有 >600 字符的记录补 `long-form` tag（追加式补丁记录），
`memo doctor` 报「存量长记录 N 条」。这一点写进 DELTA 的「刻意不做」。

## 2. 方向 B：开发期临时记忆库（session scope）

**结论先行**：不自己造压缩器——DSH 已有 `@deepseek-ai/dsh-compaction-basic`
（`thresholdRatio 0.8` / `retainRatio 0.16`，本机 asar 核实）并发 `compaction/summary` 事件
（字段：`{compactionId, summary: ContentBlock[], shadowedRange, shadowedTokenCount, provider, model, usage?: TokenUsage}`），
插件订阅即得摘要，**零额外压缩 token**。

第二次评审（用户 6 问）后补的关键设计：**临时库与主库不是两个互不相干的库，而是一套明确的读取契约**。

### 2.0 六问的答案（先说结论）

| 用户问题 | 答案 |
|---|---|
| 怎么开、会自动吗？ | **完全手动**（用户决定）。用户在会话里说「建个临时记忆库」/ `memory_session start` 才建库。插件只做**阈值提示**：累计 token ≥30k 时在上下文里提示一行「建议 snapshot」，**绝不自动建库、绝不自动压缩**。 |
| 能真的少读冗长上下文吗？ | **能，但不是压缩当前会话**。它省的是「换会话/换 agent 时的重新交代」：新会话只注入 state（≤8k 字符 = 8 段 checkpoint）+ 约定快照（≤1k），而不是让你重述或让模型回翻旧对话。当前会话内部的上下文增长仍归宿主 compaction 管。 |
| 开发完成后能关掉吗？ | 能。`memory_session close` = 冻结写入 → 触发晋升 → 产出交接文档 → 该库变只读；TTL 到期再 tombstone（30 天内可恢复）。 |
| 会不会和记忆中心分库冲突？该读哪个？ | **不冲突，定义死读取顺序**（见 2.2）：活跃临时库的 state 常驻注入；主库只常驻「约定快照」；其余一律按需检索。临时库条目带 `scope: session:<id>` 血缘，冲突时**时间戳新者胜**并标 `disputed` 并列展示，不静默覆盖。 |
| 能让记忆中心给临时库注入开发习惯吗？ | 能，且**只注入引用不拷贝正文**（见 2.3）：建库时做一次「继承查询」，把 `repo:<name>` 的 `decision`/`pref` 取 top-N 生成 ≤1k 字符的 `conventions` 段，每条带主库 id；单向流（主库→临时库，永不回写）。 |
| 关闭时能并回记忆中心 + 产出交接文档吗？ | 能（见 2.4）：按 kind 白名单晋升（`decision`/`gotcha` 可升，`state` 不升），并自动生成 `docs/handoffs/<session>.md`（六段），再往主库写 1 条 state 指向该文件，供下个 agent `memory_search` 命中。 |

### 2.1 数据模型（冻结）

- 分库：`session:<id>`，`id = <slug>-<yyyymmdd>`（**一次开发战役一个库**，多 agent 共享）。
- **1 条 `state`**：`subject=<slug>`、`predicate=checkpoint`、`value=最新 checkpoint 文本`、
  `title=「<战役名> 当前状态」`、`tags:['scratch','session:<id>']`；每次更新 `supersede` 自己（版本链可回溯）。
- **N 条 `decision`/`gotcha`**：从 checkpoint 的 `Critical Context` 与 `Errors and Fixes` 拆出，一条一句。
- **0 条 `fact`**：临时库**禁止**写 `fact`（事实属于长期库），写入即 `E_SCRATCH_KIND_FORBIDDEN`。
- checkpoint 冻结 8 段：`Intent / Concepts / Files / Errors and Fixes / Pending Jobs / Current State / Next Steps / Critical Context`；
  再加 `conventions` 段（继承来的引用，见 2.3）。**上限 8k 字符**（超出截断 `Critical Context` 之前的段，并在开头写「已截断」）。

### 2.2 读取契约（谁常驻、谁按需）

| 层 | 来源 | 进上下文的方式 | 预算 |
|---|---|---|---|
| L0 约定 | `repo:<name>` 的 `decision`/`pref`（带 `convention` 标签优先） | 建库时快照成 `conventions` 段，随 state 一起注入 | ≤1k 字符 |
| L1 战役状态 | `session:<id>` 的最新 `state` | **每次会话开始 + 每次 compaction 后**注入（`systemPrompt.context`） | ≤8k 字符 |
| L2 长期事实 | `repo:<name>` 其余记录 | **不注入**，agent 主动 `memory_search` | 按需 |
| L3 历史战役 | 已 close 的 session 库 + handoff 文档 | 不注入；交接文档路径写在主库 state 里，按需读 | — |

**冲突规则（写进 policy，不靠模型自觉）**：
1. 同一 `subject/predicate` 在 L1 与 L0 不一致 → 输出时**并列**（「约定：…（L0）」/「当前状态：…（L1）」），并给 L1 记录打 `conflict-with:l0` 标签；
2. 同一 `subject/predicate` 在 L1 内多条 `active` → 不可能（版本链保证）；
3. L1 与 L2（主库事实）冲突 → L1 新者胜但**保留 L2 并标 `disputed`**，等战役结束由 `curate` 裁决；
4. **任何情况下不把 L1 的正文写回 L0**（单向流），避免临时库污染主库。

### 2.3 继承开发习惯（单向快照 + 引用）

`memory_session start` 执行一次「继承查询」：

```
从 repo:<scope> 取 kind∈{pref,decision} 且 (tags 含 'convention' 或 hits 前 N)
→ 每条取 title + 一句 value 摘要（各 ≤80 字）
→ 组成 conventions 段，行尾附 [ref:<主库id>]
→ 写进 session state 的 conventions 段
```

- 只存**引用 + 摘要**，不拷正文 → 主库改了约定不会出现「两份真相」；
- 反向不流动：临时库的 decision 晋级时才写主库（见 2.4）；
- 约定漂移可用 `memo session refresh-conventions` 重取（战役中途主库新增约定时）。

### 2.4 收尾：晋升 + 交接文档 + 归档

`memory_session close <id> [--promote-auto|--promote-interactive]`：

1. **晋升**（默认 `--promote-auto` 只做保守规则）：`decision`/`gotcha` 满足「被命中过（hits ≥1）或 tags 含 `keep`」→ append 到 `repo:<name>`，tag `promoted-from:session:<id>`，`sourceRefs` 指回原 session 记录；`state` 永不晋升。
2. **交接文档** `docs/handoffs/<session-id>.md`（进仓库、受 git 管理 —— 用户已确认放这里）六段：
   `目标 / 已完成（含证据：commit、测试数字）/ 关键决策 / 死路（试过但不行的方案）/ 未完成与下一步 / 恢复命令`，
   头部写 `generatedAt`、`branch`、`headCommit`、`activeRecords` 统计。
3. **主库留指针**：把交接文档路径写成 1 条 `state`（`subject=<slug>`、`predicate=handoff`、`value=路径 + 一句话结论`），下一个 agent `memory_search` 即可命中。
4. **归档**：session 库打 tombstone（保留可恢复 30 天），`memo compact --purge` 才物理删除。

### 2.5 触发与开关（矩阵）

| 事件 | 默认行为 | 配置键 |
|---|---|---|
| 插件加载 | 不建库、不注入 | `session.enabled=false` |
| 用户说「建库」/ `memory_session start` | 建库 + 继承约定快照 | — |
| 会话开始（已有活跃战役） | 注入 L1 state（≤8k）+ L0 conventions（≤1k） | `session.inject=true` |
| 累计 token ≥ 阈值 | **只提示**「建议 checkpoint」，不写库、不压缩 | `session.hintTokens=30000` |
| 用户说「存快照」/ `memory_session checkpoint` | 从当前会话取摘要（有 DSH `compaction/summary` 就用它，否则让 agent 口述 8 段）→ supersede state | — |
| 用户 `memory_session close` | 晋升 + 交接文档 + 归档 | — |
| 宿主退出（插件 dispose） | flush 未落盘的 state，不 close | — |
| TTL 30 天无更新 | 标 `stale`；`sweep` 是唯一收尾者 | `session.ttlMs` |

**硬约束（用户明确）**：
- **不自动建库**——「等会话满了才压缩就没意义了」，所以建库时机由人决定，越早越好；
- **不自动压缩**——插件只提示阈值，压缩动作由 `checkpoint` 触发；
- **不自动 close**——commit/合并 ≠ 战役结束，自动 close 会误晋升、误产交接文档。
- 兜底：`memo session sweep` 列出 stale 未 close 的库并交互式晋升（防止「忘了 close」导致 TTL 吃掉落库内容）。

### 2.6 验收（机械可检验）

`eval` 新增：

- **I38 `i38-session-checkpoint`**：假 `compaction/summary` → 生成 8 段 state；缺 3 段仍成文并写「本段缺失」；
  同库二次写入 → `active=1`、版本链=2；`fact` 写入被拒（`E_SCRATCH_KIND_FORBIDDEN`）。
- **I39 `i39-session-lifecycle`**：`close --promote-auto` 后：主库新增 N 条带 `promoted-from:` 的 decision、
  `state` 未被晋升、`docs/handoffs/<id>.md` 生成且含六段标题、主库出现 1 条 `predicate=handoff` 的 state、
  session 库全部 tombstoned；重复 close 幂等。
- **I40 `i40-session-read-contract`**：L0/L1 同 subject 冲突 → 输出并列两行且 L1 打 `conflict-with:l0`；
  L2 不进入注入文本（用假 brief 断言）；注入总字符 ≤9k。
- **I41 `i41-session-conventions`**：`start` 时继承查询产出 ≤1k conventions 段、每条带 `[ref:<id>]`；
  主库修改约定后 `refresh-conventions` 更新，且**不回写主库**（断言主库行数不变）。

**UI/CLI 冒烟**：`memo session list` 显示活跃/已关闭/stale 三态；`memo brief --include-session` 才包含 L1（默认不含）。

## 3. 方向 C：分库选择在页面间保持

### C1 根因（已核实）

`versions/v0.5/ui/app.js:520` 的 tab 点击写 `location.hash = '#/' + r`，**丢掉 `?scope=`**；
读口只有 `currentScope()`（`:18`）一处，直接从 hash 解析。

### C2 修法（推荐 B：粘性分库）

新增 `versions/v0.6/ui/scope.js`（**纯函数，可单测**，不碰 DOM）：

```js
export function resolveUiScope({ hash, stored, serverCurrent, known }) {
  const fromHash = readScopeFromHash(hash);
  if (fromHash && known.includes(fromHash)) return { scope: fromHash, source: 'hash' };
  if (stored && known.includes(stored)) return { scope: stored, source: 'storage' };
  return { scope: serverCurrent ?? known[0] ?? '', source: 'server' };
}
```

`app.js` 改动 5 处：tab 点击带 scope、`currentScope()` 换成 `resolveUiScope`、切换分库写
`localStorage['sedimem.ui.scope']`、`loadScopes()` 用返回值渲染下拉、启动时若 hash 无 scope 则
`history.replaceState` 补上（不产生历史条目）。

### C3 验收（6 条机械检查）

1. `#/today` → 点「图谱」→ 请求里 `scope=` 与原来一致；
2. 图谱 → 搜索 → 卫生 → 今日，四页 `scope` 一致；
3. 直接开 `#/hygiene`（无 query）→ 用 localStorage 里的分库；
4. 清空 localStorage → 回落到 `/api/scopes` 的 `current`；
5. 分库被删（localStorage 里是旧值）→ 静默回落到 current，不 404；
6. 多标签页：另一页切分库后本页刷新跟随（`storage` 事件）。

| 数学轨道跑偏成学术玩具 | 每条必须有「机械验收 + 回滚一个 policy 字段」两件事，做不到就不合 |

## 8. 明确不做

1. 不做自动切分长记录 + 重建历史（需要 LLM，违背零依赖；`append-only` 会被破坏）；
2. 不自己实现上下文压缩器（DSH 已有 `compaction-basic`，重造只会更差）；
3. 不做 Kelly / MDP 求解器 / Information Bottleneck / 在线 Markowitz——本版没有数据量支撑；
4. 不做跨设备同步与团队共享（定位是个人本地）。

## 9. 与网上同类方案的对比结论（`docs/research/v06-vs-alternatives-2026.md`）

### 9.1 我们的结构性优势 / 劣势

| 维度 | 我们 | 同类的普遍做法 | 判断 |
|---|---|---|---|
| 真相层 | append-only JSONL + bi-temporal，任意 as-of 回查 | 多为「覆盖式」最后状态（Mem0 v3 ADD-only 是例外，但它不管冲突） | **真优势**，且是治理型插件抄不走的 |
| 跨端 | 一个 MCP server 服务 DSH / Codex / Claude Code | 绝大多数绑死一个宿主 | **真优势** |
| 离线 | 零运行时依赖，无 key 可用 | claude-mem / memsearch 默认联网或需模型 | **真优势**（也是检索弱的成因） |
| 检索 | 默认只有 BM25 + 可选语义道 | 多数默认语义检索 | **取舍**（v0.4 已留 EmbedderPort）；真欠账是「默认路径没有语义」 |
| 自动化 | 写入/裁决靠 agent 自觉 | claude-mem / Cline 有自动捕获 | **取舍**（不自动=不制造噪声，但依赖 agent 纪律） |
| 生态 | 一个插件 + 只读观察台 | 多端 UI、IDE 集成 | **真欠账**（不打算追） |

### 9.2 对比后对 v0.6 的 5 处修正（已并入本计划）

1. B 的建库从「自动」改为**完全手动 + 阈值提示**（本次用户决定，也与「不制造噪声」的取舍一致）。
2. 新增 `memo session sweep`：**孤儿库打捞**。显式 close 的设计在真实使用中必然漏交接，而 TTL tombstone 会吃掉未晋升的 decision/gotcha —— 这是数据丢失路径，必须有兜底。
3. A 的软信号从「计数」升级为**可直接重放的 `splitSuggestion: string[]`**（错误信息可操作 >> 一个数字）。
4. 新增 **CLAUDE.md / AGENTS.md 导入器**（`memo import-conventions`）：一次性格式转换，不引入运行期依赖，却直接拆掉「迁移成本」这堵墙。
5. 新增**写入侧 scope 推断模块**（`resolveScopeForWrite({cwd, explicit, env})` 纯函数 + eval 覆盖）：C 只修了 UI 读侧粘性，写入侧各客户端仍在各自猜，**记错库是最难发现的静默污染**。

## 10. LLM 接入预留（v0.7 方向，本版只留接口）

调研见 `docs/research/llm-cost-optimal-2026.md`。结论：**成本不构成约束**（三档全部落地 ≤ ¥0.5/月），真正的约束是工程形态。

| 用途 | 现状（零依赖） | v0.7 建议 | 月成本量级 |
|---|---|---|---|
| 去重/冲突裁决 | `ruleJudge` 确定性规则 | **级联**：embedding 近重复 → 规则 → 仅 borderline 调 LLM（GLM-4-Flash 免费层） | ¥0–0.1 |
| 写入抽取（长文本 → 原子记忆） | 不做（只给 `splitSuggestion` 建议） | openai-compatible 端口 + `provider=none` 默认，可接 DeepSeek/GLM/Qwen/本地 Ollama | ¥0.3（qwen-flash，20 条/天） |
| checkpoint 压缩 | 规则摘要（8 段模板） | 放最后、离线批（夜间 batch 半价） | <¥0.05 |

**架构约束（写死，防止 v0.7 走形）**：

1. 沿用已有 Port（`JudgePort` / `EmbedderPort`），LLM 只是**可选实现**；`llm.provider='none'` 时行为与 v0.6 完全一致（零依赖默认不破）。
2. **失败必须降级**：LLM 超时/超预算/报错 → 回落到规则（fail-open 到确定性路径），绝不阻断写入。
3. **成本护栏**：`llm.maxCostPerDay`、单次 `timeoutMs`、结果缓存（同 `contentHash` 不重复调用）、`--dry-run` 先估后跑。
4. **隐私明示**：调用外部 API 时必须在 `memo doctor` 与首次使用提示「本库内容将发送到 <provider>」，默认关闭、显式开启。

> 本节不产生 v0.6.0 的代码，只保证 v0.6 的接口不挡路：`session checkpoint` 已设计成「有 DSH summary 就用，没有就让 agent 口述 8 段」，v0.7 直接换成 LLM 生成即可，不需要改数据结构。
