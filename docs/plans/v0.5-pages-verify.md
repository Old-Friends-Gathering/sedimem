# v0.5.0 施工图：合并后校验线上项目站（pages-verify）

状态：进行中（2026-11-10 起）
前置：v0.4.4 的 Q10 只解决「合并前仓库里的发布面不落后」，不解决「Pages 构建没跑完 / 构建失败 / 构建落后」。

## 1. 问题

v0.4.4 加了 Q10（发布面同步），它检查三件事都发生在**仓库内**：

1. `README.md` 版本表含当前 `vX.Y.Z`；
2. `docs/index.html` 含当前 `X.Y.Z`；
3. `ci.yml` 的 `eval (I1–IN)` N 等于 `eval/run.js` 用例数。

但 GitHub Pages 是**合并之后**异步构建的：

- 构建排队 / 失败 → 仓库全绿，线上仍是旧版；
- Pages 源被人改掉（`/docs` → `/` 或换分支）→ 仓库全绿，线上什么都不对；
- 构建产物缓存 → 首页更新了但 `assets/*.png` 还是旧文件。

这三类都属于「对外唯一入口撒谎」，而 PR 门禁结构性看不到它们（PR 阶段 Pages 还没构建）。

## 2. 方案

新增 `tools/pages-verify.mjs` + `.github/workflows/pages-verify.yml`：

| 组件 | 职责 |
|---|---|
| `tools/pages-verify.mjs` | 抓线上首页，断言含 `v<当前版本>`；再抽查 `assets/{today,graph,hygiene}.png` 三个 200。Pages 构建要几分钟，默认重试 20×15s（≈5 分钟）。 |
| `.github/workflows/pages-verify.yml` | 触发：`push: main` + 每天 03:17 UTC + 手动。失败时用 `GITHUB_TOKEN` 开 issue（同标题已 open 则只追加评论），并让 job 红。 |

**它不是 PR 门禁**：PR 阶段 Pages 未构建，卡 PR 没有意义，只会逼人去 `--admin` 合并。它是**合并后监控**，与 Q10 形成「合并前 / 合并后」两段闭环。

## 3. 冻结接口（实现须服从）

```js
// tools/pages-verify.mjs
export const DEFAULT_ASSETS = ['assets/today.png', 'assets/graph.png', 'assets/hygiene.png'];
export async function currentVersion({ root })                 // → { version: '0.5.0', dir }
export function htmlMentionsVersion(html, version)             // 纯函数，只认 `v<version>` 子串
export async function verifyOnce({ url, version, assets, fetchImpl, checkAssets })
//   → { ok, reason: 'ok'|'version-mismatch'|'asset-missing'|'http-error'|'fetch-failed', detail }
export async function verifyWithRetry({ attempts=20, intervalMs=15000, sleep, log, ... })
//   → 同上 + { attempts }
```

CLI：`node tools/pages-verify.mjs [--url <url>] [--expect vX.Y.Z] [--attempts N] [--interval-ms M] [--no-assets] [--json]`
退出码：`0` 一致；`1` 不一致 / 取不到 / 资产 404；`2` 用法错误。

## 4. 验收（G1–G6）

| # | 验收项 | 证据 |
|---|---|---|
| G1 | 线上与当前版本一致时退出 0 | `pages-verify.mjs` 对 `v0.4.4` 实测 PASS（28423 字节） |
| G2 | 版本不一致时退出 1 且 reason=version-mismatch | 对 `v0.5.0` 实测 exit=1 |
| G3 | 用法错误退出 2 | `--expect nonsense` → exit=2 |
| G4 | 单测覆盖四条失败原因与重试语义 | `tests/unit/pages-verify.test.js` 8 例 |
| G5 | CI 失败会开 issue（同标题不重复） | workflow 中 `gh issue list --search` 判定 |
| G6 | 每日巡检兜底（不依赖有人合并） | `schedule: '17 3 * * *'` |

## 5. 风险与回滚

| 风险 | 处理 |
|---|---|
| Pages 构建慢于 5 分钟 → 误报 issue | 重试窗口 20×15s；仍失败时 issue 正文列出排查顺序（`gh api .../pages`、builds） |
| issue 刷屏 | 同标题已 open 只评论不新建；修复后人工关闭 |
| 站点换域名 | `--url` 可配置；workflow 里改成变量即可 |
| 回滚 | 删除 workflow 即回到「只有 Q10」的状态，不影响任何运行时行为 |

## 6. 明确不做

- 不做视觉回归（截图 diff）——成本远高于收益，且 UI 仍在动；
- 不做「构建失败自动重试 Pages」——GitHub 侧无 API 可触发，只能报告；
- 不把 pages-verify 加进分支保护 required checks——它依赖线上状态，不该阻塞代码合入。
