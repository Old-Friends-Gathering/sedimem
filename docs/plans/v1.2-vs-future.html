PLAN REVIEW · 2026-11-15

任务账本不是第二个内核

v1.2 的「任务账本」和 future-architecture 的「大框架」不是重复建设：账本只是内核的一个内容源，装配逻辑仍然只有 pack 一份。这一页把两者的位置、边界和唯一那处真重复讲清楚。

v1.1 已上线 v1.2 计划 v2 5 路红队审核 1 处真重复已合并
01

一句话结论

账本负责「记住过程」，大框架负责「决定给谁看什么」。前者是数据，后者是装配器——所以它们相邻，但不重叠。

判断标准：如果一样东西「能被 pack 消费」，它就是内容源；如果它「决定 pack 里放什么」，它就是装配器。账本属于前者，pack 属于后者。

在账本范围内

会话转录 → 段（segments）；段摘要与结构化抽取；可展开原文的锚点；任务级累计 token 与经济账。

明确不在范围内

不做预算裁剪与排序（pack 的活）；不做检索融合（search 的活）；不写 facts；不做外写审批（P3 的审批队列）。

待你拍板

brief 是否直接按 pack schema 出（推荐 A）；账本段是否允许 includeT2 场景下只给摘要不给引用。

02

现在的计划：任务账本（v1.2）

解决的问题很具体：一个开发任务跑下来，会话上下文是窗口的数倍（实测 63.9MB / 3 万 4 千事件 / 145 次宿主压缩），关掉会话就找不回来了。

约束规则为什么
只追加segments.jsonl 只 append；index.json 是派生、可重建回滚到 v1.1 时该目录被忽略，数据不丢
不新增 kind段不进 memory record（MAX_VALUE=2000 装不下，kinds 要求 halfLifeMs>0）绕开四道门、衰减、配额、slot 判 disputed
区间幂等[fromSeq,toSeq) 与 coveredSeqs 不重叠，重复捕获报 E_ALREADY_CAPTUREDfold-once：每段一生只压一次
可逆段必须带 anchor，无锚点不写不可逆的内容不允许进账本
信任与污点段自带 trust（默认 T1）与 taint[]（粘贴内容→untrusted-source）满足 I-11：T2 不注入原文
失败不阻塞session close 捕获失败只告警，--require-capture 才强制红队结论：不能因为账本写失败让用户关不掉会话
03

未来的大框架（future-architecture）

目标从「个人记忆库」升到「治理内核 + 个人端点」：内核只管治理与装配，采集交给 adapter，行动交给 daemon，均按需可选。

阶段做什么与账本的关系
P0a 地基CI 指向 CURRENT、门禁防回退、workspace、engines ≥22.15B0 的 transcript 修复依赖 22.15+ 的 zstd
P0b 语义与信任EmbedderPort、trust/taint、policy 单一来源账本段从第一天就带 trust/taint，避免回填
P1 装配pack：预算裁剪、确定性排序、AGENTS/SKILL/MCP 三种输出唯一真重复点：brief 合并进 pack，见 §05
P2 导入claude-mem / AGENTS.md / git / .ics 只读导入与 capture 同管道不同来源
P3 行动scheduler + supervisor + 审批队列账本 = 记账容器，审批 = 外写门，互不替代
P4 / P5个人端点（可选）、一致性套件无直接依赖
04

小框架落在大框架的哪一格

一句话：账本在 数据源层，pack 在 装配层，daemon 在 执行层。三层各管一件事，谁都不越界。

层问题谁负责越界示例（禁止）
数据源「过程存在哪、怎么展开」真相层 / 派生层 / 任务账本账本自己算 token 预算、自己决定哪段优先
装配「这次给 Agent 看什么」pack（含 brief 的渲染）pack 直接写账本或改真相层
执行「谁在什么时候动外部世界」daemon：scheduler / supervisor / 审批队列daemon 直接改账本内容
采集「外部信息怎么进来」adapter（Ed25519 + ingest）adapter 直写 ~/.memo
共用但不是同一件事。账本和内核共用同一个 MEMO_HOME、同一把数据锁（<memoHome>/.lock）、同一套 config/paths.js 解析；但它不共用 record 契约（values 硬顶 2000 字、kind 注册、衰减、配额都不适用）。

06

边界规则（可检查）

下面每条都能用一个断言或一次 grep 验证，不靠"大家记得"。

规则怎么验
账本不进 facts构造含段的 pack，断言 facts 数组里没有段 id（I-15）
账本不改真相层capture 前后 items/*.jsonl 行数与 hash 不变
只追加segments.jsonl 行数只增；index.json 删除后可从段重建且逐字节一致
区间不重叠重复 capture 同一区间 → E_ALREADY_CAPTURED；coveredSeqs 无交集
目录不混用grep 断言 sessions/ 与 tasks/ 的写入方分别是账本与审批
工具面不膨胀默认 MCP 工具集合 = {search, write, brief, pack}；会话工具需显式开启
07

决策与驳回

红队五路 + 未来架构比对之后，这些是定下来的，也写清楚为什么否掉另外几条。

决策理由
段落独立文件，不进 memory recordMAX_VALUE=2000 装不下 8 段；kind 注册要求 halfLifeMs>0；还要绕开衰减/配额/slot disputed
close 不阻塞捕获失败让用户关不掉会话，是最坏体验；改为告警 + --require-capture 才强制
brief 直接出 pack schema 子集（方案 A）方案 B 快一周但 P1 必然返工，且中间存在两份"简报"定义
驳回：段存 SQLite / 双写索引与零运行时依赖、真相层明文可读冲突；千段规模 JSONL 够用
驳回：自动每轮 capture五路红队一致反对；宿主与竞品的数据丢失事故全在自动路径
驳回：晋升白名单加 factfuture §5.2 明确 session 晋升只允许 decision|gotcha
驳回：brief 放完整 8 段与"30 秒接上"冲突；--full 才展开
