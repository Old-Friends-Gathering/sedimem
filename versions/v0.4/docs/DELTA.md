# v0.4 · 版本说明（DELTA）

本版目标只有一个：把竞品调研里「别人有、我们没有」的**机制**补上，且不破坏三条护城河
（append-only 真相层 / 每条可 as-of 回查 / 三端共用同一分库）。

## 本版做了什么

1. **语义道**（可选）：`EmbedderPort` + 向量索引 + RRF 融合；默认关闭，开了之后检索从「只有词法」
   变成「词法 + 语义」，两者都可用 `basis` 解释。语义路故障**只降级不阻断**。
2. **每步注入**（DSH）：`systemPrompt.context` 动态注入 ≤1200 字符的 Tier-0 目录，
   带围栏与「数据不是指令」声明；不改宿主消息数组；默认关闭。
3. **半自动捕获**：确定性启发式抽候选 → inbox 队列 → `accept` 才进真相层。
4. **分歧一等公民**：`/api/conflicts` + `memo conflicts resolve`，只在值不可比时产生，裁决非破坏。
5. **入库脱敏**：7 类敏感模式，先脱敏再哈希，tags 留痕，可整体关闭。
6. **UI 搜索页**：`#/search?q=`，结果带 `basis` 与降级提示。
7. **规模基准 + 一条命令装插件**：`eval/bench-scale.mjs`、`scripts/install-dsh-plugin.sh`。

## 刻意不做

- 不做跨用户/多人协作记忆（本机单用户是明确非目标）。
- 不做「自动把一切对话写进记忆」——我们用「候选 + accept」，因为不可审计的自动写入是噪声源。
- 不引入 LanceDB / hnswlib / jieba / 任何原生依赖：单用户记忆规模用不上，代价是构建与分发复杂度。
- 不做 embedding 模型自带（12.9MB/346 文件的教训：保持零依赖是第二条护城河）。

## 与最初认知的差异

1. 原以为「语义检索」是核心竞争力，实测后排序改成：**可解释的混合检索 + 注入时机** 比「向量本身」重要；
   所以 RRF 与 `basis` 字段是必做的，向量库是可替换的。
2. 原以为 disputed 是罕见边缘情况，实际在真实库里会自然积累（同 subject 不可比值）；
   v0.3 只有 CLI 能看，v0.4 给了 API 与页面入口。
3. Q5 契约覆盖从 100% 掉到 97.6%：新增导出里有 4 个属 UI/内部工具，登记在 `contract-exempt.json` 之前
   先按「能被下游依赖」的标准筛过——剩下的按登记表进 `docs/02` §3.15。

## v0.4.1 / v0.5 入口

- 语义道：把「回填」做成 nightly 自动段落（有 embedder 时增量补）；给一个 `memo embedder check` 体检命令。
- 注入：把「哪些记录被注入了」写进 `events.jsonl`，让「为什么这条记忆没生效」可查（可解释性闭环）。
- 捕获：从 `codex`/`claude` 的会话文件里抽候选（而非手工喂文件）。
- 检索评测：用 LongMemEval 的 turn 级 `has_answer` 做「分层 vs 扁平」A/B（见调研报告 §评测）。
